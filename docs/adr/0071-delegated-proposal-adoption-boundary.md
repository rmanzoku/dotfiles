# ADR 0071: 委譲先の提案を採用判断へ変換する境界を定める

## Context

親エージェントが、委譲先から返された可逆な残タスクを採否未決のままユーザーへ転送し、同じ一覧に
commit という正当な gate が含まれていたため、隣接する可逆項目まで確認待ちにした。

当初は、条文の判定単位が未定義であるという 2 件の仮説を立てた。

1. `可逆性と自走範囲` は、可逆性を報告全体と項目のどちらで判定するかが未定義である
2. `委譲` は、親が保持する最終判断に、委譲先が挙げた提案・推奨・残タスクの扱いが含まれるかが未定義である

baseline と revised を同一シナリオで比較したところ、チェックリストを executor に開示しないブラインド評価でも
baseline が両シナリオを通過した。とくに baseline / B は、可逆性側への追記がなくても可逆項目と gate 必要項目を
正しく仕分けた。このため、観測された失敗は可逆性条文の曖昧さではなく親の適用ミスであり、効果が観測されない
可逆性側の追記は棄却した。これは ADR 0068 で、効果が観測されない守りの条文を 9 bullet から 6 bullet へ
削減した判断とも整合する。

委譲側の当初案は、委譲先の提案について親が「採否を決める」ことを義務づけていた。しかし、採否自体が
仕様・契約・データ形式などの永続判断にあたる場合、この義務は `実装と検証` の「永続判断は既存実装・テスト・
文書・ユーザー確認に基づかない限り作らない」というルールと衝突する。評価でも「ユーザーに諮ること自体を
禁じるのか」という問題が指摘されたため、実施・見送り・ユーザー諮問から親が項目ごとに選び、理由を付す
限定形へ書き換えた。

## Decision

`.chezmoitemplates/common-rules.md` の `## 委譲` 4 番目の既存 bullet を拡張し、委譲先が挙げた
提案・推奨・残タスクについて、親が項目ごとに次のいずれかを選び、理由を付すことを定める。

- 実施する
- 見送る
- ユーザーに諮問する

理由を付さずに未決のまま転送することは禁止する。理由付きの諮問は許容し、ユーザー確認を必要とする永続判断を
親が勝手に確定することは求めない。常時読み込まれる指示面を増やさないため、新規 bullet は追加しない。

`## 可逆性と自走範囲` は変更しない。

## Consequences

### 判定例

assert、テスト、schema が期待値を固定する変更は、操作として可逆でも仕様・契約・データ形式の永続判断に
あたり得る。したがって、可逆性を根拠に自走してよい対象ではなく、既存実装・テスト・文書またはユーザー確認に
根拠がなければ、理由と選択肢を整理してユーザーへ諮問する。

一方、既存の再取得経路でデータを更新するなど、新たな永続判断を伴わず可逆性の 3 条件を満たす項目は、
同じ報告内に gate 必要項目があっても巻き込まずに実施する。

### 評価方法論の注意

外部 skill `empirical-prompt-tuning` の subagent 契約は、要件チェックリストを executor へ渡す。
単一プロンプトの改善では有効だが、プロンプトの A/B 比較に使うと期待される答えが executor に漏れ、
variant 間の差を判別できなくなる。実際にラウンド 1 は 4 体すべてが 100% となった。
variant 比較ではチェックリストを caller 側の採点用に保持し、executor には状況のみを与える。
外部 skill はローカル改変せず、この方法論上の制約を本 ADR に記録する。

### 検証

- チェックリスト非開示のブラインド評価では baseline / revised の両シナリオが通過した
- 限定形では、理由付きの諮問を許容しつつ、理由のない未決転送を防ぐ判断への書き換えが観測された
- hold-out のシナリオ C でも、実施・退避による可逆化・ユーザー諮問を項目ごとに選び、条文との矛盾指摘なく通過した
- 各セルの n は 1 であり、5 イテレーション・19 run の ADR 0068 より検証強度が低い
- 新規不明点ゼロの 2 連続クリアという収束条件には未達で、resource cutoff により打ち切った
- 検証 artifact は `.context/autonomy-unit-tuning/`（git 管理外）に置く
